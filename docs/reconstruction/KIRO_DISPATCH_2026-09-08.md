### M-06 — `MUSAEUS_FORCE_REENCODE=0` turns force-reencode **on**

`scripts/car_library/vendor/build_aac_library.py:127`

```python
FORCE_REENCODE = bool(os.environ.get("MUSAEUS_FORCE_REENCODE"))
```

`bool("0")` is `True`. So is `bool("false")` and `bool("no")` — every non-empty
string is truthy. The only values that leave force-reencode *off* are unsetting
the variable (`None`) or setting it to the empty string, which is exactly the
pair an operator is least likely to reach for. An operator who sets it to `0`
intending to *disable* the override triggers a full re-encode of the whole car
library — 10,545 files, roughly 44 hours.

Fix: parse the value rather than its existence. Truthy on `1/true/yes/on`
(case-insensitive), falsy on `0/false/no/off/""`, and decide explicitly what an
unrecognised value does — refusing loudly is better than guessing, given the cost
of guessing wrong here.

**The "grep both repos" check in the Register is already done.** This is the only
instance of the `bool(os.environ.get(...))` pattern in either repository:

- MUSAEUS: `build_aac_library.py:127` — this line, nothing else.
- ORPHEUS (`/mnt/FORGE2TB/Projects/ORPHEUS`): zero matches — across **4,891 `.py`
  files, 43 of which do use `os.environ`**. The coverage figure is given because a
  zero from a grep that reached nothing looks identical to a zero from a grep that
  reached everything, and this project has been bitten by that three times.

So M-06 is one line in one file, not a class of bug to sweep. Add a test — the
value `"0"` must not enable force-reencode — because the defect is invisible on
inspection and will be reintroduced by anyone "simplifying" the parse back to a
truthiness check.
